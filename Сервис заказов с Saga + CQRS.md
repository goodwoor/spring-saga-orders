# Пет-проект: Сервис заказов с Saga + CQRS

## Идея
Несколько независимых сервисов (заказы, оплата, склад), взаимодействующих через события. При отказе одного из шагов — компенсирующие транзакции вместо распределённой блокировки. Concептуально близко к ручной реализации того, что делает Axon Framework, но без Event Sourcing — состояние хранится в обычных таблицах, события используются только для координации между сервисами (не как источник истины).

## Стек
Spring Boot, Kafka, PostgreSQL (у каждого сервиса своя БД), Resilience4j, Docker Compose

## Архитектура — сервисы
- **Order Service** — создание заказа, хранит статус (`CREATED`, `AWAITING_PAYMENT`, `CONFIRMED`, `CANCELLED`)
- **Payment Service** — списание оплаты, хранит транзакции
- **Inventory Service** — резервирование товара на складе

## Работа с базой данных — по одной на сервис (database-per-service)

Каждый сервис владеет **своей** отдельной PostgreSQL-базой — прямое следствие микросервисного подхода, никакой сервис не лезет напрямую в таблицы другого. Это то, что делает Saga вообще нужной: без общей БД нельзя обернуть все три операции (заказ + резерв + оплата) в одну обычную ACID-транзакцию, значит нужна альтернатива на уровне приложения.

**Order Service**: таблица `orders` (id, статус, сумма, список позиций, timestamps). Статус — центральное поле, по нему движется вся Saga.

**Inventory Service**: таблица `stock` (товар, доступное количество, зарезервированное количество). Резерв — это отдельная операция `available -= N; reserved += N`, а не прямое списание, чтобы можно было откатить резерв при отмене заказа, не трогая физическое наличие товара.

**Payment Service**: таблица `transactions` (id заказа, сумма, статус: `PENDING`/`SUCCESS`/`FAILED`). Хранит попытки оплаты как отдельные записи — важно для идемпотентности: если сообщение о запросе оплаты придёт повторно (например, из-за ретрая Kafka), сервис должен увидеть уже существующую транзакцию по id заказа и не списать деньги дважды.

**Read-модель (CQRS)**: отдельная таблица `order_view`, физически может жить в той же БД, что и Order Service, или в отдельной — денормализованная, без джойнов, оптимизирована под чтение (например, сразу хранит название товаров текстом, а не только id, чтобы не ходить в Inventory Service за каждым чтением).

**Транзакционность внутри одного сервиса**: там, где меняется своя БД и одновременно публикуется событие в Kafka — классическая проблема dual write (записать в БД и в Kafka — это две отдельные операции, между ними может произойти сбой). Для полной надёжности используется **паттерн Outbox**: событие сначала пишется в отдельную таблицу `outbox` в той же транзакции, что и основное изменение данных (это уже гарантированно атомарно — одна БД, одна транзакция), а отдельный процесс (или Debezium/CDC) читает `outbox` и публикует в Kafka. Для первой версии проекта можно упростить — публиковать событие сразу после коммита без Outbox, но явно понимать этот компромисс и уметь объяснить, в чём риск (событие может не отправиться, если сервис упадёт между коммитом в БД и отправкой в Kafka).

## Работа с Kafka — топики и поток событий

**Топики** — по одному на тип события, а не один общий поток:
- `order-events` (`OrderCreated`, `OrderCancelled`, `OrderConfirmed`)
- `inventory-events` (`InventoryReserved`, `InventoryReservationFailed`, `InventoryReleased`)
- `payment-events` (`PaymentCompleted`, `PaymentFailed`)

**Ключ сообщения** — id заказа. Это гарантирует, что все события одного заказа попадают в одну партицию и обрабатываются строго по порядку (нельзя допустить, чтобы `PaymentFailed` обработался раньше `OrderCreated` из-за параллельной обработки разных партиций).

**Оркестратор как consumer** — подписан на все три топика событий (или на единый агрегирующий топик, если так проще для первой версии), при получении события смотрит на текущий статус заказа и решает следующий шаг Saga — публикует команду следующему сервису (например, `ReservePaymentCommand`) как ещё одно сообщение в Kafka, а не через прямой REST-вызов, чтобы вся координация шла через события единообразно.

**Read-модель как отдельный consumer group** — слушает те же топики независимо от оркестратора (другая consumer group — оба читают один и тот же поток, не мешая друг другу), обновляет `order_view` при каждом релевантном событии.

**Идемпотентность консьюмеров** — раз Kafka не гарантирует exactly-once "из коробки" без специальной настройки, каждый consumer (особенно Payment Service) должен уметь безопасно обработать одно и то же событие дважды — отсюда и таблица `transactions` с проверкой на существующую запись перед списанием, упомянутая выше.

## Saga — оркестрация (не хореография)
Выбрана оркестрация, а не хореография — проще для первой реализации: один явный координатор вместо распределённой логики, размазанной по обработчикам событий в каждом сервисе.

**Оркестратор** — отдельный компонент (или часть Order Service), который явно ведёт последовательность шагов и знает про откат на каждом из них:
1. Создать заказ (`CREATED`)
2. Запросить резерв товара в Inventory Service
3. Если резерв успешен → запросить оплату в Payment Service
4. Если оплата успешна → подтвердить заказ (`CONFIRMED`)
5. Если оплата не прошла → компенсация: отменить резерв товара → отменить заказ (`CANCELLED`)
6. Если резерв товара не удался → сразу отменить заказ, до оплаты дело не доходит

Каждый шаг — событие в Kafka (`OrderCreated`, `InventoryReserved`, `PaymentCompleted`, `PaymentFailed` и т.д.), оркестратор подписан на результаты и решает, что делать дальше.

## CQRS — разделение записи и чтения
- **Write-модель** — сервисы выше, оптимизированы под транзакционные операции
- **Read-модель** — отдельная денормализованная таблица/БД (например, `order_view`) с уже готовым для быстрого чтения представлением заказа (статус, товары, сумма, история — без джойнов между тремя сервисами)
- Синхронизация: Order Service публикует события, отдельный consumer обновляет read-модель асинхронно
- Важно продумать: что видит пользователь, пока read-модель ещё не обновилась (eventual consistency) — можно показывать "статус обрабатывается" на этот промежуток

## Circuit Breaker (Resilience4j)
На вызовах между сервисами (если где-то остаются синхронные REST-вызовы помимо событий, например для первоначального запроса) — обернуть в `@CircuitBreaker`, задать fallback-поведение при недоступности одного из сервисов, не заваливать систему ретраями при каскадном отказе.

## Что не делаем (осознанно упрощаем относительно "настоящего" Axon-подхода)
- **Event Sourcing** — не восстанавливаем состояние проигрыванием истории событий, хранится текущее состояние напрямую в таблицах
- **Управление таймаутами саги** — можно добавить упрощённо (например, если Payment Service не ответил за N секунд — считать шаг неудачным), но без полноценного персистентного планировщика
- **Идемпотентность продюсера/консьюмера Kafka** — эта тема идёт отдельно в System Design блоке, здесь не обязательна с первой версии, можно добавить позже как улучшение

## Нагрузочное тестирование
В отличие от URL shortener, этот проект не про высокие нагрузки — здесь важнее корректность (правильно ли отрабатывает компенсация при отказе), чем цифры RPS. Метрика для резюме здесь другая: не производительность, а надёжность — например, "гарантированная консистентность при отказе любого из трёх сервисов, проверено N сценариями отказа".

## Что это даёт для интервью
- Реальный опыт с eventual consistency и компенсирующими транзакциями — не только в теории
- История про осознанный trade-off: почему Saga, а не распределённая транзакция (2PC), и почему оркестрация, а не хореография для первой реализации
- Понимание "изнутри", что делает такой framework как Axon — весомее, чем формальное знание его API
- Материал для вопроса "расскажи о сложном архитектурном решении" на behavioral-секции
