# saga-orders

Пет-проект интернет-магазина: заказ, склад и оплата — три сервиса, у каждого своя PostgreSQL. Общей транзакции на «создать заказ, зарезервировать товар и списать деньги» нет. Шаги связывает **сага (Saga)**: цепочка локальных операций. Если шаг не удался, предыдущие откатываются (например, снимается резерв).

Координатор — сервис заказов: по статусу заказа решает, какую команду слать дальше.

## Стек

Java 21, Spring Boot 4.1.1, Spring Cloud Gateway, Apache Kafka, PostgreSQL, Liquibase, Maven (несколько модулей), MapStruct, Docker Compose. Фронт — Vite.

## Архитектура

Сага с оркестрацией: один координатор в сервисе заказов.

Статусы заказа:

1. `CREATED` — заказ сохранён, запрошен резерв на складе
2. `AWAITING_PAYMENT` — товар зарезервирован, запрошена оплата
3. `CONFIRMED` — оплата прошла
4. `CANCELLED` — не хватило товара (оплату не запускали) или оплата не прошла (резерв сняли)

[Схема допустимых переходов статусов](docs/message-flow-order-saga.html#status-machine). Из `CONFIRMED` и `CANCELLED` никуда.

Прочие особенности: своя база на сервис; исходящие сообщения — через таблицу `outbox` в той же транзакции, что изменение данных; остаток на складе блокируется `SELECT FOR UPDATE` до конца транзакции резерва или отката.

![Успешный путь саги](docs/saga-happy-path.svg)

Отказ резерва: `ReserveFailed` → `CANCELLED`, оплату не запускаем. Отказ оплаты: `PaymentFailed` → `RevertReserveCommand` → `ReserveReverted` → `CANCELLED`. `RevertReserveFailed` статус заказа не меняет.

Те же схемы в HTML: [поток саги](docs/message-flow-order-saga.html), [слои и модули](docs/infrastructure-layers-modules-and-runtime.html).

## Решения и компромиссы

**Сага, а не распределённая транзакция (two-phase commit).** Три отдельные базы нельзя обернуть в одну ACID-транзакцию без 2PC. 2PC держит блокировки на время всех участников и плохо переживает падение координатора. Сага меняет это на последовательность локальных транзакций и компенсацию. Цена — согласованность не мгновенная: между шагами заказ уже есть, а оплаты ещё нет.

**Оркестрация, а не хореография.** Поток читается в одном месте (сервис заказов), проще отлаживать компенсации. Цена — заказ становится узлом, от которого зависят склад и оплата; смена сценария почти всегда трогает этот сервис.

**Координатор внутри сервиса заказов, а не отдельный процесс.** Меньше движущихся частей, статус саги = `orders.status`. Цена — у сервиса две роли (домен заказов и координация), его нельзя масштабировать отдельно от оркестратора, доменная модель обрастает переходами саги.

**Поллер `outbox`, а не Debezium.** Не нужен Kafka Connect и разбор WAL. Пауза поллера — 50 мс после прохода. Цена — лишние запросы к своей базе и нет CDC «из коробки».

## Гарантии и ограничения

Запись в `outbox` и изменение заказа / резерва / платежа — одна транзакция: «сохранили в базе, но не собирались слать» не бывает.

Дальше поллер шлёт в Kafka и только потом ставит `PROCESSED`. Если процесс умрёт между этими шагами, строка останется `NEW` и уйдёт снова. Это доставка **как минимум один раз**, не ровно один.

Поэтому потребители не должны выполнять побочный эффект дважды:

- оплата — одна запись на `order_id`; повтор команды возвращает тот же исход;
- склад — нашли резерв по `order_id` → тот же исход, остаток не списываем повторно; UNIQUE `(order_id, item_id)` — страховка на гонку.

Поллер читает пачку `NEW` без `FOR UPDATE SKIP LOCKED`. Два экземпляра сервиса могут взять одну строку; для одного локального процесса это не проблема.

Не делается (и не планируется в этом объёме): таймауты саги, отдельная read-модель (CQRS), Circuit Breaker.

## Запуск

Нужны Docker и JDK 21. Maven Wrapper уже в репозитории.

Разработка (инфра в Docker, приложения в IDE; рабочий каталог запуска — **корень репо**):

```powershell
docker compose up -d
```

Затем Gateway, Order, Inventory, Payment. Postgres каждого сервиса поднимется сам (`profile db`).

Весь стек в контейнерах (сборка образов долгая):

```powershell
.\scripts\docker-up.ps1
```

Если образы уже есть: `.\scripts\to-docker.ps1`. Сначала остановите приложения в IDE (порты 8081–8084). Обратно в IDE: `.\scripts\to-idea.ps1`.

| Что | Порт |
|-----|------|
| Gateway | 8081 |
| Inventory / Order / Payment | 8082 / 8083 / 8084 |
| Kafka | 9092 |
| Консоль Kafka | 8090 |
| pgAdmin | 5050 (`admin@example.com` / `admin`) |
| Фронт (Vite) | 5173 |
| Postgres order / payment / inventory | 5433 / 5434 / 5435 |

## Демо

Открыть http://localhost:5173 и нажать одну из трёх кнопок:

- успешный заказ → `CONFIRMED`
- отказ резерва (нехватка товара) → `CANCELLED`
- отказ оплаты → снять резерв → `CANCELLED`

Статус на экране обновляется сам, пока не станет конечным.

## Замер при 3–5 параллельных клиентах

Одна копия каждого сервиса, 19.10.2026: Windows, i5-12400F (12 потоков), 16 ГБ, JDK 21. Приложения на хосте, Kafka и PostgreSQL в Docker. pgAdmin и Kafka UI на время прогона остановлены. Поллер `outbox` — пауза 50 мс, пачка уходит одним ожиданием, у слушателей Kafka `concurrency = 3`, остаток товара блокируется на время транзакции резерва. Самая широкая волна — 5 одновременных `POST`. Где заказы/с перестают расти, прогон не искал. `POST /order` отвечает сразу; время до конечного статуса считается отдельно, от отправки `POST` до `GET`.

p50 — медиана. p95 при N=20 — 19-е значение из 20, при N=30 — 29-е из 30. Максимум — самое медленное. Все строки ниже дошли до нужного статуса.

| Сценарий | Режим | N | p50 | p95 | Максимум | Заказов/с | Дошли |
|----------|--------|---|-----|-----|----------|-----------|-------|
| Успешный, 1 товар | по одному | 20 | 0.69 с | 1.04 с | 1.10 с | — | 20 |
| Успешный, 1 товар | 5 сразу | 30 | 4.49 с | 6.35 с | 6.40 с | 4.23 | 30 |
| Успешный, 10 товаров | 5 сразу | 30 | 3.74 с | 5.04 с | 5.04 с | 5.26 | 30 |
| Отказ оплаты, 1 товар | по одному | 20 | 0.91 с | 1.98 с | 1.98 с | — | 20 |
| Отказ оплаты, 1 товар | 5 сразу | 30 | 9.15 с | 12.48 с | 12.64 с | 2.28 | 30 |
| Отказ оплаты, 10 товаров | 5 сразу | 30 | 6.38 с | 7.78 с | 7.85 с | 3.61 | 30 |

Отказ оплаты длиннее: после неуспешной оплаты ещё откат резерва. Один товар в пачке медленнее десяти: резервы ждут одну строку остатка.

HTTP через Gateway, один клиент, ошибок не было. В таблице время ответа, не время саги. `POST` — последовательное создание успешного заказа. При N=50 максимум совпадает с тем, что nearest-rank называет p99.

## Тесты

Два слоя. Оба ходят в PostgreSQL и Kafka из Testcontainers.

**Один сервис** — пакет `saga.single` в своём модуле. Поднимается только этот сервис. Сюда входят гонка остатка, автомат статусов, повтор команды, локальный отказ резерва и оплаты.

**Три сервиса вместе** — только три критичных сценария: успешный заказ, нехватка товара, отказ оплаты. Модуль `services/e2e`, тесты в `SagaFlowIT`. Стенд `SagaFlowStand` запускает три отдельных процесса `java -jar`. Сервисы сканируют один пакет `saga`: в одном процессе они подхватят чужие бины. Заказ создаётся через `POST /order`, склад и оплата отвечают сами.

`.\mvnw.cmd test` сквозные тесты не запускает. Класс называется `SagaFlowIT`, его берёт Failsafe на фазе `verify`, когда jar уже собран.

| Путь | Тест |
|------|------|
| Заказ доходит до `CONFIRMED` | `SagaFlowIT` |
| Отказ резерва и отказ оплаты, возврат остатка | `SagaFlowIT` |
| Локальный отказ резерва и отказ оплаты | `InventoryCompensationTest`, `PaymentFailureTest` |
| Повтор резерва и повтор оплаты не списывают второй раз | `InventoryReserveTest`, `PaymentIdempotencyTest` |
| Два резерва последней единицы, остаток не ниже нуля | `InventoryReserveTest` |
| Запрещённый переход статуса не меняет заказ | `OrderSagaStatusTest` |

Из корня репозитория: `.\mvnw.cmd test`. Вместе со сквозным путём: `.\mvnw.cmd verify`.
