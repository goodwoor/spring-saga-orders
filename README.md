# saga-orders

Пет-проект интернет-магазина: заказ, склад и оплата — три сервиса, у каждого своя PostgreSQL. Общей транзакции нет, шаги связывает сага: цепочка локальных транзакций с компенсацией при отказе. Координатор — сервис заказов.

## Стек

Java 21, Spring Boot 4.1.1, Spring Cloud Gateway, Kafka, PostgreSQL, Liquibase, MapStruct, Maven, Docker Compose, Vite.

## Архитектура

Статусы заказа:

1. `CREATED` — заказ сохранён, запрошен резерв.
2. `AWAITING_PAYMENT` — товар зарезервирован, запрошена оплата.
3. `CONFIRMED` — оплата прошла.
4. `CANCELLED` — не хватило товара или оплата не прошла (резерв снят).

Из `CONFIRMED` и `CANCELLED` переходов нет. [Схема переходов](docs/message-flow-order-saga.html#status-machine).

![Успешный путь саги](docs/saga-happy-path.svg)

- Отказ резерва: `ReserveFailed` → `CANCELLED`, оплата не запускается.
- Отказ оплаты: `PaymentFailed` → `RevertReserveCommand` → `ReserveReverted` → `CANCELLED`.

Схемы в HTML: [поток саги](docs/message-flow-order-saga.html), [слои и модули](docs/infrastructure-layers-modules-and-runtime.html).

## Решения

**Сага вместо 2PC.** 2PC держит блокировки во всех базах и плохо переживает падение координатора. Цена саги — согласованность в конечном счёте: между шагами заказ уже есть, а оплаты ещё нет.

**Оркестрация вместо хореографии.** Весь поток виден в одном месте, компенсации проще отлаживать. Цена — любой новый сценарий затрагивает сервис заказов.

**Координатор внутри сервиса заказов.** Меньше процессов, статус саги — это `orders.status`. Цена — у сервиса две роли, координатор не масштабируется отдельно.

**Поллер `outbox` вместо Debezium.** Не нужны Kafka Connect и разбор WAL. Цена — опрос базы каждые 50 мс.

**`FOR UPDATE` вместо `@Version` на остатке.** При замерах в логах БД было много конфликтов версии и повторов; пессимистичная блокировка показала себя лучше. Строки блокируются по возрастанию id, чтобы избежать дедлоков.

## Гарантии

- Изменение данных и запись в `outbox` — одна транзакция.
- Доставка — как минимум один раз: если процесс упадёт между отправкой в Kafka и отметкой `PROCESSED`, сообщение уйдёт повторно.
- Повтор команды безопасен: оплата ищет запись по `order_id`, склад — резерв по `order_id`; уникальные ключи страхуют от гонки.

## Запуск

Нужны Docker и JDK 21. Рабочий каталог — корень репозитория.

Инфраструктура в Docker, приложения в IDE:

```powershell
docker compose up -d
```

Затем запустить Gateway, Order, Inventory и Payment. Postgres каждого сервиса поднимется сам.

Весь стек в контейнерах: `.\scripts\docker-up.ps1` (первая сборка долгая), дальше `.\scripts\to-docker.ps1`. Перед этим остановите приложения в IDE: порты 8081–8084 должны быть свободны. Вернуться в IDE: `.\scripts\to-idea.ps1`.

| Что | Порт |
|-----|------|
| Gateway | 8081 |
| Inventory / Order / Payment | 8082 / 8083 / 8084 |
| Kafka / Kafka UI | 9092 / 8090 |
| pgAdmin | 5050 (`admin@example.com` / `admin`) |
| Фронт | 5173 |
| Postgres order / payment / inventory | 5433 / 5434 / 5435 |

## Демо

На http://localhost:5173 три кнопки: успешный заказ, нехватка товара, отказ оплаты. Статус обновляется до конечного.

- **Один сервис** (`saga.single`): гонка остатка, автомат статусов, повтор команды, локальные отказы.

## Известные ограничения

- Откат резерва удаляет его строки, поэтому дубль команды резерва после отката зарезервирует товар заново.
- Своего обработчика ошибок в слушателях нет: после повторов сообщение пропускается, заказ зависает в промежуточном статусе. DLT и таймаутов саги нет.
- `POST /order` не валидируется: цену присылает клиент.
- Одна «битая» строка `outbox` останавливает всю очередь сервиса; обработанные строки не удаляются.
- Поллер без `SKIP LOCKED`: две копии сервиса отправят одно сообщение дважды.

## Доработка сценариев отказа

- Резерв получает статус (`RESERVED` / `REVERTED` / `FAILED`) вместо удаления; на `ReserveCreated` для отменённого заказа Order шлёт откат.
- Обработчик ошибок с DLT и поиск зависших заказов по времени в статусе.
- Валидация `POST /order`, цену считает склад.
- Для `outbox`: отдельный статус для строк, которые не удаётся отправить, `SKIP LOCKED`, чистка обработанных.
